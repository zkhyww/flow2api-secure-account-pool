# Flow2API 无插件持久账号设计

## 目标

Google 账号只登录一次，登录状态写入 Flow2API 现有账号表并由现有 Windows 当前用户加密机制保护。服务重启或 Windows 重启后，不加载扩展、不输入配对码、不手动重连；生成任务到来时自动启动内置浏览器，任务空闲后自动关闭。账号池、调度、并发、熔断、积分与日志继续沿用现有实现。

## 已确认根因

- `Token` 与数据库持久字段为 `google_cookies`。
- `BrowserCaptchaService._load_token_cookie()` 错读不存在的 `token.cookie`，导致已持久化账号不能注入内置浏览器。
- `_persist_context_cookies_to_token()` 错写不存在的 `cookie` 字段，浏览器刷新后的会话不能回存。
- 当前“浏览器添加账号”仍通过临时加载扩展导入，不是真正的原生无插件添加。
- 空闲回收会关闭 resident tab，但没有在最后一个业务标签页回收后可靠关闭整个浏览器运行时。

## 主链路

1. 调度器照常选择账号和项目，并把 `token_id` 传入 personal captcha 服务。
2. personal 服务按需启动浏览器，在独立 browser context 中从该账号的 `google_cookies` 注入会话。
3. 在同一个 context 中获得 reCAPTCHA、浏览器指纹和必要会话信息，并交给现有 Flow 请求链路。
4. 成功后把更新过的 Google 会话合并回同一账号的 `google_cookies`；写入时继续走现有 DPAPI 加密。
5. 账号标签页空闲到期后关闭；最后一个业务标签页关闭且无在途任务时，关闭浏览器进程并清理临时 profile。
6. 下次任务或服务重启后重复 1–5，不依赖扩展在线。

## 首次登录与失效恢复

- 管理页“添加 Google 账号”启动隔离的有头内置浏览器，不加载 Flow2API 扩展。
- 用户只负责完成 Google 登录或 Google 要求的二次验证。
- 后端从该临时 browser context 原生提取并标准化会话，调用现有 TokenManager 新增或更新账号；原始凭据不进入公开响应和日志。
- 登录完成后窗口自动关闭。若 Google 后续撤销会话，只将该账号标记为需要重新登录，并提供账号级“一键重新登录”。
- 现有扩展保留为高级故障备用，但不是正常运行、重启恢复或新增账号的依赖；personal 模式下不显示插件连接告警。

## 扩缩容

- 账号数量和浏览器数量解耦。数据库可保存现有账号池规模，不因账号数启动同等数量浏览器。
- 至少允许 3 个并发槽位；按现有 dense-pack/调度策略优先利用已启动 worker，压力增加时扩到配置上限 10 个浏览器。
- 每个账号使用独立 context；并发请求不得把 Cookie、指纹或 reCAPTCHA 归因到其他账号。
- 无任务时所有浏览器可退出，账号状态仍在数据库中。

## 安全边界

- 不读取、打印、打包或在诊断中返回 Cookie、ST、AT、密码、完整 URL、原始提示词或媒体内容。
- Cookie 只在数据库解密边界与内置浏览器 context 之间流动；写盘继续复用现有 DPAPI，不增加第二套凭据库。
- 公共诊断仅允许 `stage`、`status`、`error_class`、`token_id`、`worker_count`、`has_media`、`attempt_count` 等白名单字段。
- 不修改 `D:\codex项目\Framefield-Studio`，不 push、发 PR、发布或部署。

## 验收标准

- 回归测试能先复现 `cookie`/`google_cookies` 错配，再证明修复后正确读写且不泄漏明文。
- 无扩展连接时，三个现有账号在 personal 模式可被调度，并保持账号隔离。
- 模拟进程重启后，无需配对即可从数据库恢复所选账号的浏览器绑定。
- 原生添加账号流程不复制、不加载扩展目录，重复点击只启动一个窗口。
- 空闲 TTL 后最后一个业务标签页和浏览器进程均退出；新任务可重新拉起。
- 至少覆盖 3 个并发槽位、最多 10 个 worker 的配置边界与按需扩缩。
- 全量测试、静态合同、JS 语法、`git diff --check` 通过后，才进行一张低成本、无敏感内容的真实图片 smoke。
