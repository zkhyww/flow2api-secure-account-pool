# Flow2API 本地增强版与上游原版差异

> 目标是尽量以小补丁增强本地使用，不把项目改造成另一套完全不同的架构。上游原有 README、许可证和 attribution 保留。

## 1. 这份本地增强版主要多了什么

相对上游原版，本地工作树主要增加或加固了这些能力：

- 本地多账号安全调度：复用原有 Token、LoadBalancer、ConcurrencyManager 和 personal browser 主路径，不另建第二套账号库或浏览器调度器。
- 动态并发与冷却：优先使用已有活跃账号的安全容量；429 做降并发和冷却，其他错误按真实类别处理。
- 浏览器按需启动和 idle 回收：普通生成仍使用临时 Profile；账号持久 Profile 只在添加账号、显式重新登录或认证恢复时启动浏览器，结束后关闭。普通 personal pool 与这些认证浏览器共享同一个最多 10 个存活浏览器进程 lease；lease 从启动前持有到 shutdown 清理完成，原有启动并行度闸门继续只负责抑制启动尖峰。
- 无插件本地账号添加与恢复：每账号有独立本机持久登录 Profile；Cookie/ST/AT 失效后先走协议刷新，再按需从该 Profile 自动恢复。一次刷新失败只进入退避或人工重登状态，不会永久停用账号。
- 升级迁移：升级前已有账号需要逐个正常重新登录一次以建立持久 Profile；完成后同一机器、同一 Windows 用户下的服务重启可继续恢复。跨机器不迁移 Profile，每台机器都要分别登录。
- Windows 本地体验：`start-flow2api.pyw` 一键启动，以及管理页里的 Windows 登录后自启开关。
- 公开 capability 目录和测试页增强：图片参数、视频 8/10 秒能力、会员边界等由服务端 metadata/resolver 统一处理。
- 影策兼容 API：OpenAI Images 风格图片端点和 NewAPI 风格视频任务端点，继续复用现有 GenerationHandler/FileCache，不再造第二个上游客户端。
- 安全加固：multipart 总体积、TTL/后台任务资源清理、远端媒体 allowlist、逐跳 redirect 校验、DNS 公网校验、TLS 验证、下载字节上限和媒体代理固定解析。
- 离线 synthetic 压力/恢复测试与无人值守测试器：默认不读取真实账号凭据、不执行真实 Flow。

## 2. 哪些上游能力没有被替换

本地增强版仍把以下上游组件当作事实源：

- Token 和现有数据库：账号事实源。
- LoadBalancer：账号选择主入口。
- ConcurrencyManager：并发计数和上限主入口。
- personal browser 相关服务：浏览器生命周期、账号绑定和验证码主路径。
- FlowClient / GenerationHandler：真正的提交、轮询、媒体解析主路径。
- FileCache：媒体落盘主路径。

本地补丁的原则是“能增强现有对象就不另起炉灶”。

## 3. 影策兼容层的明确边界

- 图片兼容 API 可以返回 `b64_json`；如果 provider 给出符合官方 allowlist、HTTPS、标准端口且无 userinfo 的媒体 URL，也可以直接返回 OpenAI Images `url`。
- 视频兼容 API 不能直接把上游 URL 当 `/content` 的重定向目标。远端视频必须安全下载成本地文件，registry 只保存本地文件名。
- 显式 HTTP 媒体代理使用固定 IP 的安全隧道，TLS 仍验证原始官方域名；不支持的代理类型 fail-closed，不做不安全降级。
- 影策视频 task registry 当前是进程内状态。服务重启后，旧 task ID 不保证继续可查询。
- mask、模型参考图、分辨率等如果现有上游能力不能保证语义，会直接 fail-closed，而不是假装支持。

## 4. 本地账号池的使用边界

- 200 个账号是验收规模，不是硬编码账号上限。
- 同时存活浏览器进程最多 10 个，这是本机资源保护线，不是账号数量限制；普通池、添加账号、重新登录和认证恢复共享同一个 live-process lease，不另建一套账号/浏览器调度器。
- 默认行为倾向“单号先吃满安全容量，再启用下一个”，而不是平均把所有账号浏览器都打开。
- `is_active` 仍只表示用户主动启停。认证失败只更新独立认证恢复状态，公开层只显示“正常 / 等待自动恢复 / 稍后重试 / 需要重新登录 / 已停用”。
- 认证恢复得到的新 ST 只作为内存候选：先执行 ST→AT，再用返回身份核对目标账号；只有同一账号才一次性写回候选 ST/AT。身份不匹配或转换失败时 fail-closed，不覆盖目标账号。显式重新登录不会直接原地修改旧 Profile：已有 Profile 先安全复制到隔离候选，候选复用旧登录态；身份确认成功后，凭据、Profile 引用、认证成功状态和显式启用状态在单个 SQLite 事务中提交，事务成功后才清理旧目录；事务失败或身份不匹配则保留旧引用并清理候选；没有旧 Profile 时才创建空候选。目录删除若被临时文件锁阻塞，会在 Profile 根内留下只含不透明 key 的 cleanup marker，并在下一次候选创建时重试，避免无跟踪孤儿长期累积。
- 账号登录态和会员能力仍由 Google/Flow 决定；本地增强不会绕过验证码、Passkey、两步验证、会员或风控。
- 认证恢复只持久化白名单状态/错误类别；原始异常、上游响应正文、完整 URL 和候选凭据不进入公共 API 或认证恢复日志。
- 账号持久 Profile 是本机认证恢复来源，不作为日志/API/导出字段，也不作为跨机器备份格式；普通生成 worker 继续使用临时 Profile。同机备份必须在服务停止后将 `data/flow.db` 与整个 `data/account_profiles/` 成对保存。

## 5. Windows 本地增强

- `start-flow2api.pyw`：已有服务就只打开管理页，没有服务才启动当前项目自己的 venv + `main.py`。
- Windows 自启开关：真实状态来自固定 Task Scheduler 任务；管理页不保存一个脱离系统事实的布尔值。
- 本地增强不会自动修改真实系统任务，除非用户在管理页明确操作开关。

## 6. 为什么这些改动尽量保持“小补丁”

上游还会继续变化。改动越集中，未来同步上游时越容易审查：

- 尽量不改公共接口之外的无关代码。
- 通过小 service/adapter 包住 Windows、影策等本地特性。
- 安全行为先有 RED 合同，再做最小 GREEN。
- 旧公开模型/旧 API 路由继续做回归，避免为了新功能破坏原调用方。

## 7. 建议的 future upstream sync 流程

本项目**没有声称已经实现自动上游同步**。建议以后按人工可审查流程更新：

1. 配置/更新 `upstream` remote，只获取上游变更，不直接覆盖当前主工作树。
2. 从当前本地版本创建专门的同步测试分支。
3. 合入或 rebase 上游变更，逐个处理冲突；优先保留上游结构，只把本地增强重新贴到必要位置。
4. 跑全部自动门禁：focused、安全套件、full pytest、compileall、静态/隐私检查、`git diff --check`。
5. 检查是否出现重复造轮子、上游已经实现同类能力、模型目录变化、验证码/浏览器生命周期变化。
6. 自动门禁全绿后，只做受控的小规模真实 smoke；先单任务，再小并发，不因为同步而直接扩大真实消耗。
7. Codex/独立 reviewer 检查差异和真实 smoke 结果后，再决定是否合并到本地主分支。

不要把“能 clean merge”当成“已经兼容”。真正完成同步的标准是：差异可解释、自动门禁全绿、受控真实 smoke 没有新回归。

## 8. 当前交付范围

本地增强版以 Windows 本地使用为主。Zeabur、Linux 云端登录入口、生产部署和自动 upstream sync 都不在本次交付范围内。
