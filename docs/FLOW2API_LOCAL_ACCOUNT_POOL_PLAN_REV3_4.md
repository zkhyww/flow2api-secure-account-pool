## 2. 用户目标（大白话）

在现有 Flow2API 上补齐“本地多账号自动工作”的能力：平时不让大量浏览器常驻；有任务时优先把一个账号的安全并发用满，再启用下一个账号；浏览器按需启动、空闲回收；任务提交后自动等待并取回媒体；遇到限流、余额不足、登录失效或外部错误时能准确换号、冷却或提示，不能盲目重提导致重复扣积分。

## 3. 规模与硬边界

- `200 个账号`只是本次性能和管理验收规模，不是代码硬上限。
- 账号数量继续跟随上游 Token/账号管理能力；禁止新增 `accounts` 表、第二套账号仓库或 `MAX_ACCOUNTS = 200` 一类限制。
- 同时存活的浏览器进程最多 10 个；这是本机资源保护上限，不等于账号上限。
- 账号元数据必须懒加载/分页或按需读取，不得因账号总数增加而同时打开全部 Profile 或浏览器。
- 暂不实现 Zeabur、云端登录入口、Linux 密钥存储或生产部署。
- 禁止修改 `D:\codex项目\Framefield-Studio` 及其 worktree。
- 禁止 push、PR、Issue、发包、部署、迁移真实生产数据；未经用户另行明确授权，不创建 Git commit。

## 4. 不造轮子的架构原则

必须优先复用并增强现有实现：

- `Token`、现有 token 表和 `TokenManager`：账号唯一事实源。
- `LoadBalancer`：账号选择和单号优先策略的唯一入口。
- `ConcurrencyManager`：显式并发上限、运行中计数和动态学习的唯一入口。
- `_PersonalBrowserPoolService` / `browser_captcha_personal.py`：浏览器、resident tabs、token/project affinity、token pool、空闲回收和内存压力回收的唯一实现。
- `FlowClient`、`GenerationHandler`、现有 `Task`/项目机制：提交、轮询、媒体获取和错误处理的主路径。
- Extension 保持兼容，但第一主路径是 personal browser；不另建 Browser Manager、Resource Governor、账号数据库或浏览器调度器。

只有测试先证明现有抽象无法承载某个必需行为，才允许增加小型适配对象；新增对象不得复制上述服务的状态或职责。

## 5. 安全与隐私不变量

- 不绕过 CAPTCHA、Google 风控、账号限制或付费/会员限制。
- 新增日志和诊断只能使用：阶段、探针、错误类别、HTTP 状态、账号内部 ID、是否有媒体、计数和耗时。
- 新增代码不得记录 Cookie、ST、AT、验证码 token、密码、完整 URL、原始提示词、原始媒体、完整响应体。
- 不从浏览器或 CLI home 导出凭据；真实测试只使用用户已配置到 Flow2API 的账号状态。
- 凭据持久化增强必须在现有 token 事实源上做兼容包装，不得复制到第二张表或第二套配置文件。
- 锁、任务状态和额度记录不得包含凭据或原始提示词。

## 6. 调度语义（必须同时满足）

1. 账号数量无硬上限；200 个账号时管理和调度仍可用。
2. 未知账号的默认安全并发从 3 开始；如果用户显式上限小于 3，则服从显式上限。不能把 `-1` 当成无限并发直接压上游。
3. 优先继续使用已经活跃且有安全容量的账号；该账号达到当前安全容量、冷却、失效或额度不足后，才启用下一账号。
4. 显式配置的并发上限必须继续生效；动态学习不能超过用户显式上限。
5. 成功只能缓慢增加学习容量；429/明确限流必须立即降低学习容量并进入冷却，不能直接永久禁用整个账号。
6. 不把认证失败、额度不足、会员不足、策略拒绝、外部 5xx、网络超时都误判成 429。
7. 最多 10 个浏览器进程；达到内存阈值或浏览器上限时排队，不继续启动。
8. 浏览器 worker 可以预创建为轻量对象，但浏览器进程必须按需启动；任务结束后由现有 idle reaper 回收。
9. token/project affinity 必须保留，避免同一账号在多个浏览器间无谓抖动。
10. 并行任务必须真实并行，不得退化为全局串行；资源不足时只排队超出的任务。

## 7. 任务与额度语义

- 每个外部请求必须有稳定幂等键；相同键重试只返回/继续同一任务，不得再次提交上游。
- 状态至少区分：`created`、`reserved`、`submitting`、`accepted`、`polling`、`succeeded`、`failed`、`unknown`。
- 一旦上游可能已接受但本地没有得到确定响应，进入 `unknown`，只允许查询/恢复，禁止盲目重提。
- `accepted` 后必须异步轮询并自动解析媒体；客户端断开不能自动取消已接受的上游任务。
- 额度在提交前预留；同一幂等键只预留一次。明确失败可释放，成功结算，`unknown` 保持冻结直至对账/人工处理。
- 进程重启后必须能恢复 `accepted/polling/unknown` 任务，不重复提交。

## 8. 分批施工（每一批都必须 RED → GREEN）

### Batch 0：固定基线与测试夹具

目标：让基线门禁可信，不改生产合同。

- 修正 `tests/test_api_captcha_fingerprint.py` 的夹具：测试不得用未完整初始化的 `FlowClient.__new__()` 假造生产对象；生产 `(token, userAgent)` 合同保持不变。
- 保存基线失败证据和修复后结果。
- 禁止借此重构 `FlowClient`。

验收：现有测试从 `49 passed, 1 failed, 3 subtests passed` 变为全绿；只能改测试夹具或最小测试辅助代码。

### Batch 1：复用现有调度器实现“单号优先 + 动态安全容量”

目标文件优先限定为：

- `src/services/concurrency_manager.py`
- `src/services/load_balancer.py`
- 相关现有配置入口（仅当 10 浏览器上限确需统一）
- 新增针对性测试；不得新增第二套调度服务。

RED 用例至少覆盖：

1. 两个空闲账号时稳定选择第一个；第一个仍有学习容量时继续选择第一个，而不是平均摊开。
2. 第一个达到容量/冷却/失效后才选择第二个。
3. 未配置并发（`-1`）的账号初始有效容量为 3，不是无限；成功后可继续逐步增加，不要求长时间低速试探。
4. 连续成功时容量保守增加；429 时立即降级且进入冷却；冷却结束后从降级容量恢复学习。
5. 显式上限永不被学习值突破。
6. release/重复 release 不产生负数；取消和异常路径不泄漏槽位。
7. 账号集合为 0、1、200 及大于 200 时，不存在硬编码截断。
8. browser count 对外配置和运行时解析都不能超过 10；减少配置后现有多余 worker 由原有关闭逻辑回收。

GREEN 原则：只在 `ConcurrencyManager` 增加最小学习状态和在 `LoadBalancer` 调整排序/选择；继续由现有 acquire/release、pending 和 affinity 工作。

### Batch 2：幂等提交、状态恢复和异步取媒体

优先复用现有 `Task`、数据库任务方法、`GenerationHandler` 和 `FlowClient`。

RED 用例至少覆盖：

1. 同一幂等键并发两次只发生一次上游 submit。
2. submit 超时但是否接受未知时进入 `unknown`，不得自动再次 submit。
3. `accepted/polling` 在客户端断开后继续轮询并最终保存媒体状态。
4. 服务重启后恢复未完成任务，不重复提交。
5. 媒体为空、策略拒绝、认证失败、额度不足、429、外部 5xx 分别归类。

如现有 task 表字段不足，只允许兼容性扩展该事实源；禁止新建平行任务库。

### Batch 3：额度预留与错误驱动换号

RED 用例至少覆盖：

1. 同一幂等键只预留一次额度。
2. 明确提交失败释放；成功结算；`unknown` 不释放也不二次扣减。
3. 额度不足不提交并切换可用账号。
4. 429 只触发账号动态并发降级/冷却，不误伤其他账号。
5. 登录失效、会员等级不足和策略拒绝不作为可无限重试错误。

优先扩展 token/task 现有字段与统计方法，不增加 `accounts` 或独立 quota 数据库。

### Batch 4：账号登录态兼容加固与按需浏览器生命周期

- 复用 token 的 `google_cookies`/ST/AT 和 personal browser token binding。
- Windows 本地加密若实现，必须对现有字段做向后兼容的加解密包装和可回滚迁移；不保存密码，不产生第二份凭据。
- 复用现有 resident tabs、worker affinity、idle reaper、memory reclaim。
- 验证不同账号不会串 Cookie、串 project、串 CAPTCHA 上下文。
- 验证最多 10 个浏览器、按需启动、空闲关闭、内存压力排队/回收。

### Batch 5：管理可观测性与 200+ 规模验收

- 管理页显示账号状态、学习并发、当前 in-flight、冷却原因/剩余时间、额度摘要和浏览器占用摘要。
- 页面和 API 不返回凭据；200+ 账号采用现有列表接口的分页/懒加载增强，不把 200 写成上限。
- 使用纯假数据完成 0/1/200/500 账号调度和页面/API 性能测试。

### Batch 6：受控真实 Flow 验收

前置条件：所有自动测试、静态门禁和隐私扫描通过。

- 使用已导入的现有账号，不读取或输出凭据。
- 先单账号单任务，再小并发；只有用户授权后扩大。
- 只记录白名单诊断字段和是否拿到媒体。
- 真实测试失败时先归因，不盲目重提。
- Omni Flash 横竖 8 秒与 10 秒均已完成白名单验收；正式目录保留 8 秒并默认 10 秒，Veo 3.1 仍只开放 8 秒。

### Batch 7：无额度合成压力与恢复量化

- 只使用纯假账号、内存数据库/临时数据库和 fake browser runtime；默认断网，不启动 Chrome，不读取真实账号、数据库或凭据。
- 复用现有 `LoadBalancer`、`ConcurrencyManager`、personal browser pool、幂等任务恢复和分页实现；不得另建账号池、调度器、凭据库或浏览器管理器。
- 功能合同覆盖 0/1/200/500 假账号、3/5/10 worker、dense-pack、第 11 个排队、429 冷却、取消/超时/异常/重复释放、同键单次提交和重启恢复不重复提交。
- 性能采样与功能断言分开；报告只输出批准的聚合白名单字段，不以极窄绝对耗时作为单元测试门禁。
- Zeabur、整机重启、长期无人值守和生产部署继续排除在本批之外；真实 10 路图片边界已在 Batch 8 补验。
